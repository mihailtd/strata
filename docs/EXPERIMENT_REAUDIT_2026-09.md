# Experiment Re-Audit — September 2026

## Why this exists

Two things happened close together: (1) the repo got reorganized into `experiments/`/`benchmarks/`/`evals/` (see `METHODOLOGY.md`), making it possible for the first time to see, per experiment, whether it actually graduated into a live `apps/runtime*` module; (2) we found and fixed a real integrity violation — `apps/harness/coordinator/subagent.py` and two now-deleted scripts were silently fabricating "agent-generated" code while reporting unconditional success (see `agent_sandboxes/README.md`'s "Removed" section).

Finding #2 raised an obvious question: if that got past review, what else has? This is a systematic re-audit of every cluster in `experiments/` (29 clusters, 3 parallel research passes) plus a cross-reference of every already-shipped `apps/runtime` module against which runtimes/model sizes actually exercise it. It answers, per cluster: worth revisiting or not (why), integrated in runtime A but untested in runtime B, worth a full harness-driven end-to-end eval, worth combining with another cluster now that something's been settled.

**Read the next section first.** It's more urgent than the categorization exercise that motivated this document.

## 🚨 Critical: production-default features backed by fabricated or synthetic-as-real data

None of these route through the harness-coordinator mechanism that caused the original incident — this is a separate, independently-discovered pattern of the same shape: a number presented as an empirical measurement of the real system that is actually generated by code designed to produce that exact answer.

### 1. `weibull_hazard_gating` — SEVERE, default-on in production, zero real measurement, zero paper trail

`RangeStatisticGate(weibull_hazard_enabled=True, bollinger_bands_enabled=True)` is instantiated by default in `apps/runtime/server.py` and consumed live in `apps/runtime/mtp_draft.py`'s draft loop, on **both the 4B and 9B serving paths** (confirmed live in `apps/runtime-ipwf` too). Its only performance justification — `experiments/runtime/speculative/weibull_hazard_gating/` — never loads a model. Both benchmark scripts hand-construct "realistic synthetic token streams" from a hardcoded acceptance-decay curve (`[0.85, 0.72, 0.58, ...]`) specifically shaped to contain the signal the gate is designed to detect, and the reported "tok/s" comes from a **hardcoded linear latency formula** (`t_base_single * (1.0 + 0.12 * k)`), not a timed decode. Zero hits for "Weibull," "Bollinger," or this cluster's name anywhere in `docs/DECISIONS.md`.
**Action**: treat as unverified in production. Needs the same treatment `cache_length_counter` and `serving_gate` got — real prompts, real model, real graph-replay timing, arms toggled live via the existing `/api/engine/set_speculative_range_gate` endpoint — before the next time anyone cites this gate's speedup.

### 2. `latent_variable_glasso` — SEVERE, justifies a shipped runtime default

`WeightFoldingEngine(scale_mode="surgical")` — the **runtime default** per `docs/DECISIONS.md` §52 — traces its hyperparameters (`top_k=15`, `max_conflict_modules=2`) directly to this cluster's "one true conflict edge" finding. All four scripts in the cluster share `compute_cross_layer_activation_deltas`, whose own docstring says *"Simulates realistic forward activation deltas"* — it generates a synthetic input matrix with a deliberately injected low-rank shared-factor term, multiplies it by the real trained LoRA weights, and reports the result as "Empirical Results Across Trained v4 Domain Adapters." The real adapter weights are used; the activations — the entire empirical basis for the headline claim — are fabricated.
**Mitigating factor**: `surgical_notch_sweep` (a different, later cluster) independently reaches a similar qualitative conclusion using purely analytic real-weight math on real v7 adapters (2.2×–4.3× selectivity) — so the *practical* notch-filtering behavior has a real, non-fabricated confirmation elsewhere. The claims unique to LV-GLasso (rank(L)=299, the specific conflict edge, "conditional orthogonality") do not.
**Action**: re-label the unique LV-GLasso claims as a methods demonstration, not an empirical finding, or re-run with real forward-pass activations the way `probe_stacking_merit.py`/`probe_capca_premise.py` correctly do it. Cite `surgical_notch_sweep` as the real anchor when the topic is "does surgical notching work."

### 3. `speculative_mtp_distillation` — recommends something to production that a real experiment already contradicts

Operates entirely on a `SimulatedMTPDraftHead` (`d_model=512`, nowhere near Qwen3.5-4B's real dimensions) with synthetic random weights and tokens. Never touches `apps/runtime/mtp_draft.py`. Yet its README's "Architectural Integration" section tells readers to use `HuberDistillationLoss` when training domain-specialized draft heads for the live engine. **`docs/DECISIONS.md` §63 already ran this on the real EAGLE draft head** (real domain fine-tuning, all 6 canonical v7 domains, real GPU) and found the *opposite*: the stock non-domain-adapted head beats every domain-tuned variant by 10–34%, because the 1-layer head's limited capacity means any domain fine-tuning — robust loss or not — causes representation collapse.
**Action**: retract the README's integration advice; point to §63 as the authoritative answer.

### 4. `poet_activation_crosstalk` — milder version of the same pattern

The headline script generates "activation probe inputs" as `X = torch.randn(...)` (explicitly commented as synthetic), multiplies by real trained deltas, and reports it as measuring "dynamic activation perturbations... on Qwen3.5-4B." A **sibling script in the same directory**, `probe_4way_poet_notch.py`, already does this correctly with real forward hooks — its results just aren't what's quoted in the README.
**Action**: cheap fix — swap the README's headline numbers for `probe_4way_poet_notch.py`'s real ones. No new engineering needed.

### 5. `experiments/frontier/*` (all 5 files) — fabricated result tables, not measurements

None of the four "Frontier Inventions" (tree speculation, early exit, jump tokens, block sparsity) load a model; three of the four don't even `import torch`. Every reported number (cosine similarity retention, exit probabilities, "net throughput speedup") is a hand-authored Python literal. Zero references anywhere in `docs/DECISIONS.md`.
**Action**: not worth revisiting in current form — these don't test anything, they assert a scorecard. Lower urgency than #1–3 because nothing shipped depends on them (see the "already superseded" note in the per-cluster table below for two partial exceptions).

### 6. `experiments/agentic/benchmark_predictive_prefold.py` — honestly-labeled mock, but presented unqualified elsewhere

The class is literally named `MockVRAMFoldingEngine` and the script is honest about being a mock in its own code. But `docs/DECISIONS.md` §64 presents its output (66.7% pre-fold hit rate, 0.76ms perceived latency) as "Empirical Benchmark Results" without qualification, and the *mechanism* it validates (`NotearsCausalScheduler`, `async_prefold`) is genuinely wired live into `apps/runtime/server.py`. This is different from #1–4: the mock is disclosed in code, just not carried through to where the numbers get cited. See Category 4 below — this is the clearest candidate for a real DSH-driven re-measurement.

### Documentation staleness (not fabrication, but actively misleading)

- **`live_speculative_engine`'s README** says the ring-buffer rollback mechanism isn't wired into the live decoder ("`ring_buffer_wired: false`"). Direct code check: `apps/runtime/bucketed_speculative.py` **does** now import and use `RingBufferReplayEngine` — the wiring happened the same day the README was written and the doc never caught up.
- **`activation_inertia_probe`'s README** presents its `L_inert` training-penalty proposal as unattempted future work. It was actually tried three times (v5/v5b/v5c) and failed each time (uniform suppression with no ASR change, degenerate `<pad>`-token silencing, lost to a crash) — recorded in `docs/DECISIONS.md` §39 but never reflected back into this cluster's own README.

## Category 1 — Not worth revisiting (closed, rigorous, stands as-is)

These reached a real, well-evidenced conclusion on real models/weights, with no synthetic-as-real substitution, and nothing about the reorg or the harness incident changes that.

| Cluster | Verdict |
| :--- | :--- |
| `cache_length_counter` | Root-caused a real GPU wedge, fixed it, and honestly withdrew an earlier optimistic speedup number once the fix revealed speculation is currently a net loss (0.78×) vs. the graph-autoregressive baseline. |
| `draft_model_0_8b` | Structural, hardware-level negative result (decode is depth-bound, not param-count-bound) — not a tuning miss, won't change on a different draft candidate at the same depth. |
| `loop_profile` | Correctly killed a proposed kernel-fusion effort by implementing and measuring the "obvious fix," which made things 1.65% slower. |
| `serving_gate` | Closed the load-bearing question ("does eager speculation actually beat the real graph-capture baseline") and directly motivated the bucketed-capture design that shipped. |
| `step_budget` | Four independent "reduce the work" attempts all ~1.0×; correctly concludes the loop is launch-bound, not work-bound — matches `loop_profile` and `serving_gate` independently. |
| `poet_decomposition` | Clean dimension-analysis negative result (`O(ρd²)` beats `O(rd)` the wrong way) — will not change with a different model or runtime. |
| `orthogonality_headroom` | Real trained A/B with an honestly-documented implementation bug caught mid-experiment; correctly retired since its only consumer (adapter stacking) is independently dead. |
| `preflight_svd_probe` (subspace overlap + PiSSA) | The strongest self-correction chain in the audit — caught its own randomized-SVD bug, retracted an earlier "free at serving time" claim. Both halves cleanly closed. |
| `architecture_comparison` (id_kron vs LoRA) | Correctly retracted an earlier erroneous audit (parameter count was reported backwards) and redid it properly; stock LoRA wins by a wide, non-marginal margin. |
| `surgical_notch_sweep` | The clean, real-weight anchor for "does surgical notch filtering work" — cite this one, not `latent_variable_glasso`, when the topic comes up. |

## Category 2 — Worth revisiting or finishing (real, but incomplete)

These aren't fabricated — they're real measurements that stopped short of a usable conclusion, or real findings never written up anywhere durable.

- **`activation_init_premise` (CAPCA)** — real Gram-trick SVD on real activations found the spike premise holds strongly (336× chance) but relevance is ambiguous (2.28×, in the probe's own self-defined "judgement call" band). The result JSON exists (`results/benchmarks/capca_premise.json`, dated) but the verdict was never written up in `docs/DECISIONS.md`, `CURRENT.md`, or `TODO.md`. Cheap to close out: write the verdict, and consider the small training A/B (tens of GPU-minutes per the PiSSA costing convention) that could actually resolve the ambiguity.
- **`riemannian_metric`** — the weight-Gramian geodesic distance is definitively closed (flat, backwards, already excised from `dynamic_team_router.py`'s routing). But the one thread the README itself flags as open — the same geodesic distance computed on **activation** covariance (real `n<p` regime) rather than weight Gramians — has never been run and isn't pre-falsified by anything measured so far.
- **`m1_vs_m2_regime`** — real paired-bootstrap comparison, but only ever run on 2 of the 4 canonical domains (astral: trending, CI not resolved; postgresql: resolved win). `duckdb` and `financial` have never had the same comparison run, despite the whole adapter fleet being named after this decision as if it were fleet-wide.
- **`state_replay`'s branching/tree "unlock"** (part b of that cluster) — the commit_fwd-replacement idea (part a) is correctly closed as a net loss. But the ring buffer's capability for time-travel steering and local beam search is confirmed real and mostly untapped; the width-2×depth-4 tree case was found to need only 8 live nodes (within the existing `max_depth=8`) plus 0.26MB of KV forking — described in `docs/DECISIONS.md` as "a small piece of plumbing, not a memory-infrastructure project." Nobody has picked this up.
- **`weibull_hazard_gating`** — also listed in the critical section above; the fix here is a real remeasurement, which makes it as much a Category 2 item as a Category 0 one.

## Category 3 — Integrated in runtime A, worth testing in runtime B (or model size B)

Full detail from the cross-runtime audit; ranked by "already live in production, never measured there."

**Structural finding first**: the 27B serving path (`apps/runtime/native_27b_engine.py` and its `runtime-triton` counterpart) never actually uses the "shared module library" — `server.py`'s `load_inference_engine()` returns immediately on the `is_27b` branch, before reaching any of the code that sets up `novel_peft`, `cuda_graph`, `range_statistic_gate`, `dynamic_team_router`, `notears_causal_scheduler`, `bucketed_speculative`, or `mtp_draft`. Every one of those is really a **4B/9B-only** library that reimplements nothing for 27B; 27B has its own independent (and largely separately-benchmarked) implementations of the same concepts. Keep this in mind below — "shared" doesn't mean "used everywhere."

| Feature | Live where | Benchmarked on | Real gap |
| :--- | :--- | :--- | :--- |
| `macd_speculation_circuit_breaker.py` | 4B + 9B (unconditionally, inside `bucketed_speculative.py`) | Nothing real — synthetic acceptance-pattern simulation only | **Sharpest gap in the audit**: gates real speculative decode on two model sizes, zero real-model measurement ever. |
| `range_statistic_gate.py` | 4B + 9B | Nothing real — both `range_statistic_gating` and `weibull_hazard_gating` are synthetic logit simulations | Same shape as above; see critical section #1. |
| `mtp_draft.py` / `bucketed_speculative.py` | 4B + 9B (default on in `runtime-ipwf`) | 4B only — zero hits in any 9B benchmark | Live on 9B by default, never once measured there. |
| `cuda_graph.py` (`FoldedCudaGraphDecoder`) | 4B + 9B | 4B only | Same pattern — runs on 9B today, only measured on 4B. |
| `dynamic_team_router.py` | 4B + 9B | 4B only (one real GPU benchmark, one synthetic) | Live multi-expert router on both sizes, only ever measured live on 4B. |
| `fused_norm.py` | 4B + 9B, **but the fold optimization is explicitly disabled for 9B** (`fold_norms_enabled = (...) and not is_9b`) | 4B only | Not just untested on 9B — coded to skip it. Worth finding out why and whether it's safe to enable. |
| `notears_causal_scheduler.py` | 4B + 9B (unconditional) | Only via the mocked `benchmark_predictive_prefold.py` | Live on both sizes, "tested" only against a `time.sleep` simulation. See Category 4. |
| `alpha_calibration.py` | Model-agnostic endpoint, accepts any adapter dir | 4B only | 9B and 27B experts exist with their own scorecards but have never been run through alpha calibration. |
| `cut_set_router.py` | Not wired into any server | Proven live on real 9B in a standalone harness (`benchmark_9b_cut_set_live_pipeline.py`) | Inverted gap: the harness proof exists, the integration into `runtime-ipwf`'s actual server doesn't. Wiring is the next step, not more benchmarking. |
| `copula_routing.py`, `gee_trajectory.py` | Not imported by any serving code | Synthetic data only (`np.random`-generated) in both cases | Prior question to "which model size": neither has ever touched a real model's activations at all. |
| `adaptive_tree_speculator.py` | Present, but not wired into any request-serving path — reachable only via standalone benchmark scripts that instantiate `Native27BEngine` directly | 27B only | Gap in both directions: never tried on 4B/9B, and not actually "live" for 27B either despite being on the shipped-module list. |
| `state_handoff_27b.py` | 27B-only by design (`server.py`'s `is_27b` multi-agent branch) | 27B only | Not a model-size gap — a **runtime-parity** gap: `runtime-triton` (meant to replace 27B serving) doesn't vendor it, so the multi-agent tensor-handoff feature has no home if that migration completes. |
| `w4a16_loader.py`, `triton_w4a16.py` | 27B only, vendored in both `apps/runtime` and `apps/runtime-triton` | 27B only | Not a real gap — 4B/9B are served unquantized by design; quantizing them doesn't answer a question this project cares about. |

## Category 4 — Worth a full harness/DSH-driven end-to-end eval

The DSH SDK integration (`evals/dsh_agent/`) makes a class of "is the scaffolding actually good, not just present" question answerable for the first time. Best candidates, ranked:

1. **`experiments/agentic/benchmark_predictive_prefold.py` / `NotearsCausalScheduler`** — the strongest candidate. The scheduler and `async_prefold` are genuinely wired live into `server.py` with a real dashboard control; the quantified benefit (66.7% hit rate, 0.76ms perceived latency) has only ever been measured against `MockVRAMFoldingEngine` and 15 hand-scripted turns. A real DSH agent driving genuine multi-turn tool use through the live server, with the real folding engine, would either confirm or correct a number `docs/DECISIONS.md` §64 currently presents as settled.
2. **`macd_speculation_circuit_breaker.py` / `range_statistic_gate.py`** — since these gate live production behavior on two model sizes with zero real validation (Category 3's sharpest gaps), a DSH-driven realistic-workload run is a more honest substitute for the synthetic benchmarks than another synthetic benchmark would be.
3. **`cut_set_router.py`** — first wire it into `runtime-ipwf`'s server (it's proven standalone on 9B already), then a DSH-driven multi-tool-call session is the natural way to validate the wiring actually improves real agentic throughput, not just the standalone harness's synthetic pipeline.

## Category 5 — Worth combining, now that something's settled

- **`state_replay`'s branching/tree unlock + `weibull_hazard_gating`'s early-exit gate.** A tree with a live per-branch early-abort gate is exactly what both half-finished ideas are reaching for separately. Prerequisite: `weibull_hazard_gating` needs the real-measurement fix from the critical section first — building a combined feature on top of an unverified gate would just compound the risk.
- **`poet_temporal_compression`'s state ring buffer (integrated) + `state_replay`'s branching capability.** Both already touch `apps/runtime/state_ring_buffer.py`; the compression work and the not-yet-built branching/tree consumer are two ends of the same infrastructure that haven't been connected.
- **`riemannian_metric`'s open activation-covariance thread + `copula_routing`/`gee_trajectory`.** All three are statistical-routing signals that have never been validated against a real model's actual activations (the first is explicitly flagged as such; the other two have never touched a real model at all). Rather than three separate synthetic-or-half-real validation passes, one shared real-activation statistical-routing evaluation would answer all three at once and would be the first real-data test any of them has had.
- **`apps/runtime/jump_streamer.py` (shipped, simple, real) vs. `experiments/frontier/benchmark_jump_tokens.py` (fabricated, complex, never shipped).** Not a combination so much as a calibration exercise: compare the real macro-injection implementation's actual measured impact against what the fabricated benchmark predicted for the more elaborate design, to get an honest sense of how far off the other three frontier inventions' fabricated numbers likely are, by extension.

## How to use this document

- If you're about to cite a number from any cluster marked with a 🚩 flag above, don't — re-verify against real data first, or use the "real anchor" this document names instead.
- If you're picking up new work and want a well-scoped, low-risk starting point: `activation_init_premise`'s write-up, `m1_vs_m2_regime`'s missing 2 domains, or `weibull_hazard_gating`'s real re-measurement are all cheap and would close real gaps.
- If you're deciding whether a runtime feature needs cross-model-size testing before you trust it: check the Category 3 table before assuming "shared module" means "validated everywhere it runs."
- New entries should follow this document's format (rigor check, integration status, explicit category) rather than starting a new one — update this file in place as clusters get resolved.
